# Contributing

## Setup and checks

Python 3.10 with [uv](https://docs.astral.sh/uv/); the lock pins PyTorch for CUDA 12.1
on Linux x86_64. Always run through the lock, never system Python.

```bash
uv sync --locked --extra tuning --extra scoring --extra tracking --extra mazes
uv run --locked --extra tuning --extra scoring --extra tracking --extra mazes pytest -q core/tests
uv run --locked pytest -q core/tests/test_mdlm.py::test_name      # one test
uv run --locked ruff check core main.py frontier.py scripts experiments

uv run --locked python main.py +experiment=smoke               # CPU smoke run: 2 steps of tiny MDLM on Sudoku
uv run --locked python main.py +experiment=<name> --cfg job    # print the composed config without running
uv run --locked python main.py mode=evaluate evaluation.checkpoint=/path/last.ckpt   # mode: train|evaluate|sample
uv run --locked python frontier.py evaluation.checkpoint=/path/last.ckpt            # pretrained sampling grid
```

The default `main.py` (no overrides) is a full GPU MDLM Sudoku-hard training run.
Outputs go to `core/outputs/` and dataset caches to `core/data_cache/`; both are
Git-ignored. Tests start their own local Ray clusters. Some sampler tests compare
against snapshots in `core/tests/fixtures/`; the byte-level ones run only on Linux
x86_64. `docs/validation/compatibility.md` is generated by
`scripts/docs/compatibility_table.py`, and a test fails when it is stale.

## Configuration model

- `main.py` → `core/training/runner.py:run`, composed from `configs/config.yaml`;
  `frontier.py` uses `configs/frontier.yaml`.
- Each component is a Hydra group with a `_target_`; algorithm configs reference
  `${model}`, `${process}`, `${parameterization}`, etc. Constructors receive explicit
  dependencies, never the whole root config.
- Switching mathematical families needs a full recipe in `configs/experiment/`
  (`# @package _global_`, `override /group: ...`). Changing only `algorithm=` does
  **not** swap the matching process, model, schedule or sampler. Copy a verified recipe
  and check it with `--cfg job`. Paper presets are listed in `docs/guides/paper-recipes.md`.
- Experiment-level groups: `configs/sweep/` (Hydra multirun case expansion for
  `core.sweeps.prepare`), `configs/ablation_path/`, `configs/feedback/`,
  `configs/inference_policies/`, `configs/time_map/`. `configs/task/battery/` and the
  `algorithm_definition` block of prepared configs are older names for "task suite" and
  "recipe definition".
- Shared modifiers are toggled by top-level blocks in `config.yaml`:
  `self_conditioning`, `block_diffusion`, `token_feedback`, `variable_length`.
- A saved run config is fully resolved: when re-evaluating with
  `--config-path <run> --config-name config`, override both `output_dir` and
  `hydra.run.dir`.

## Ownership boundaries

Read `docs/concepts/architecture.md` and `docs/concepts/component-contracts.md` before
changing a boundary.

- **Algorithm** (`core/algorithms/`, `core/modifiers/hybrid/`): training-loss assembly
  and model→prediction endpoints. `loss(tokens, loss_mask, corruption_mask=...)` returns
  `{loss, loss_sum, num_tokens}`. Every diffusion family runs on `HybridDiffusion` with
  one or more views; a family class overrides only the hooks that differ. It does *not*
  own the reverse-time loop: `generate` delegates to a sampler.
- **Sampler** (`core/samplers/`): state initialization, time progression, stopping and
  NFE accounting (NFE counts network calls, including terminal ones). Fixed-grid samplers
  share `loop.py`; `composed.py`, `policies.py` and `correctors.py` compose update rules
  and commitment policies; `requirements.py` holds the checks a sampler runs on attach.
  Entropy-bounded, adaptive ODE and autoregressive samplers keep their own control flow.
- **Math components**: `processes/`, `noise_schedules/`, `time_sampling/`,
  `representations/`, `parameterizations/` (posterior vs plug-in vs score vs
  Gaussian-prior; the same `[B,L,V]` shape does not mean interchangeable), `objectives/`.
- **Models** (`core/models/`): one `ModularDiT` with input, time, self-conditioning and
  output slots chosen in YAML; `CausalDiT` keeps its own KV-cache path.
- **Training** (`core/training/`): the Lightning `TrainingModule` owns optimizer, EMA,
  checkpointing, logging and `post_optimizer_step` hooks, not diffusion equations. It
  passes only `input_ids`, `loss_mask` and `corruption_mask` to `algorithm.loss`.
  Validation loss is logged as `val/nll` even when it is not a likelihood.
- **Tasks** (`core/tasks/`, data in `core/data/`): implement `core/tasks/base.py`; own
  datasets, collation, `prepare_generation` (prompt and fixed mask, never leaking
  answers) and metrics that score final token sequences independently of the generator.
- **Modifiers** (`core/modifiers/`): self-conditioning, block diffusion (including
  block-size mixtures and E2D2), multi-view hybrids, token feedback, variable length.
- **Sweeps** (`core/sweeps/`): a thin layer over Ray tasks and Optuna. `prepare.py`
  turns a Hydra multirun into a plan; `nested_tuning.py` runs each case as an outer
  study over training candidates and inner per-sampler studies, selected on validation,
  then scores only the winner on the test split. Terms are defined in
  `docs/guides/experiments.md`.
- **Analysis** (`core/analysis/`): reads nested-tuning run trees for the worked
  examples' `analyze.py` scripts.

## Conventions

- Contracts are constructor arguments and runtime checks, not static types. Not every
  combination is compatible; see `docs/validation/compatibility.md` and
  `docs/validation/coverage.md`.
- Masks: `loss_mask` = contributes to the loss, `corruption_mask` = may be corrupted,
  `prompt_mask` True = fixed during generation.
- Training and sampling prediction paths are separate, so temperature, top-k and top-p
  never alter the training objective.
- Prefer Hydra composition and native Ray/Optuna machinery over experiment-specific
  scripts. Changing an existing experiment's protocol needs new case and output names;
  `nested_tuning` checks the stored `protocol.json` on resume.
- New components: YAML in the relevant `configs/` group plus a doc page under `docs/`
  (see `docs/extending/`). Add an algorithm class only when orchestration genuinely
  differs; most new methods are recipes.
- Worked examples follow the rules in `experiments/README.md`: one protocol per example,
  named after the question, self-contained, verified by `analyze.py` and a CPU test.
